# Event Processing Architecture

## 1. Introduction

This document outlines the current architecture of the Keep event processing pipeline. The system uses a modular, microservice-based architecture to decouple ingestion from processing, supporting high-throughput messaging backends like **Apache Kafka** while maintaining support for **Redis** (ARQ).

### 1.1 High-Level Overview

The architecture consists of three main components:
1.  **API Gateway (Ingestion)**: Lightweight entry point that validates requests and offloads raw events to a message broker.
2.  **Messaging Layer**: Pluggable abstraction (`EventProducer`/`EventConsumer`) supporting Redis and Kafka.
3.  **Event Handler Service (Worker)**: Dedicated service that consumes events, runs business logic (parsing, enrichment, workflows), and persists data.

## 2. Key Components & Implementation

### 2.1 API Gateway (Ingestion)

The API (**`keep-api`**) acts as a dumb pipe. It does *not* parse or process events synchronously. Its responsibilities are strict:
*   Authentication (API Key / JWT)
*   Basic Size Validation
*   Producing to the Message Broker

**Key File**: [`keep/api/routes/alerts.py`](file:///Users/yarin/keep/keep/api/routes/alerts.py)

**Code Example**:
The `receive_event` endpoint extracts the raw body and uses the `event_producer` dependency to offload it immediately.

```python
# keep/api/routes/alerts.py

async def receive_event(
    provider_type: str,
    request: Request,
    # ... dependencies
    event_producer: EventProducer = Depends(get_event_producer),
) -> dict[str, str]:
    # Use the abstract event producer (Redis or Kafka)
    task_name = await event_producer.produce(
        event=event,
        tenant_id=authenticated_entity.tenant_id,
        provider_type=provider_type,
        # ... other metadata
    )
    return JSONResponse(content={"task_name": task_name}, status_code=202)
```

### 2.3 Event Handler Service (Processing)

The Worker (**`keep-event-handler`**) is the brain of the operation. It runs independently from the API and consumes messages from the configured broker.

**Responsibilities**:
1.  **Consumption**: Loop that polls Redis or subscribes to Kafka topics.
2.  **Parsing**: Converts raw bytes -> Provider-specific Object -> Standard `AlertDto`.
3.  **Enrichment**: Applies mapping rules, topology, and property extraction.
4.  **Deduplication**: Calculates fingerprint and handles duplicate suppression.
5.  **Persistence**: Saves to Postgres and Elasticsearch.
6.  **Workflows**: Triggers automation workflows based on conditions.

**Key Files**:
*   **Consumer Logic**: [`keep/event_handler/core/kafka_consumer.py`](file:///Users/yarin/keep/keep/event_handler/core/kafka_consumer.py)
*   **Core Processing**: [`keep/common/event_management/process_event_task.py`](file:///Users/yarin/keep/keep/common/event_management/process_event_task.py)

## 4. Legacy Architecture (Reference)

*Note: This describes the system prior to the separation of concerns. It is kept here for historical context.*

The legacy architecture was a monolithic design where the API worker thread performed synchronous parsing and provider resolution before enqueuing a job to Redis.
*   **Blocking**: Large payloads could block the API thread during parsing.
*   **Coupling**: Worker logic and API logic shared the same deployment lifecycle.
*   **Redis-Only**: Hard dependency on Redis preventing high-throughput event streaming.

The current architecture resolves these issues by offloading the "heavy lifting" to the asynchronous worker layer.
